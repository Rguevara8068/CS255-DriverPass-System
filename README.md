# System Analysis and Design

The client for this project was DriverPass, a company that wanted to help students prepare for their driving tests. They wanted an online system that would allow students to create accounts, take practice tests, review training materials, and schedule driving lessons. The system also needed to help employees manage appointments, student information, and instructor schedules. Another important feature was the ability to receive updates from the DMV about driving rules, policies, and test questions. The main goal was to create a system that would make it easier for students to access the resources and training they needed to prepare for and pass their driving tests, while also helping employees manage daily tasks more efficiently.

I think I did well at understanding the requirements for DriverPass and using them to create the different UML diagrams. In my use case diagram, I included the main users, such as students, secretaries, drivers, the IT officer, and the owner, along with the tasks they needed to perform. I made sure to include important features like scheduling, changing, and canceling driving lessons. My activity diagrams showed the steps needed to complete different tasks, while my sequence diagram helped me understand how information moves through the system. I also created a class diagram to show how students, appointments, drivers, vehicles, and training packages are connected. I think creating these diagrams helped me get a better understanding of how DriverPass would work and how all the different parts of the system fit together.

If I could go back and change part of my project, I would work on both my UML use case diagram and class diagram. With the use case diagram, I had trouble organizing the actors and use cases without having too many lines crossing over each other. I spent a lot of time moving things around to make it easier to read. When I reviewed my class diagram, I realized I had made a few mistakes that needed to be fixed. Some of the classes still had the default operations from the template instead of methods that matched what the system needed to do. I also noticed that some relationships between classes, like appointments and training packages, needed to be clearer. I had to go back through the requirements to figure out what needed to be changed. If I were to do these diagrams again, I would plan out the layout and review the class attributes, methods, and relationships more carefully before finishing them. This experience taught me that even small details can make a difference in how well a diagram explains the system.

To understand what the users needed, I went through the DriverPass interview and paid attention to what each person wanted the system to do. For example, students needed a way to schedule driving lessons, take practice tests, and review training materials, while secretaries needed to keep track of appointments and make changes when needed. I used this information when creating my UML diagrams to show how each person would use the system. I also had to think about security since not everyone should have access to the same information. For example, an IT officer would need different access than a student. I think understanding what the users need is one of the most important parts of designing a system. If you don't take the time to understand their needs, you could end up leaving out important features or creating a system that doesn't work the way the client expected.

When designing the software, I would first make sure I understand what the clients needs and wants are, also what the system needs to do. I would go through the requirements, break them down into smaller parts, and figure out how each of the users would utilize the system. I found that creating UML diagrams, such as use case, activity, sequence, and class diagrams, helped me see how everything connects before starting development. One thing I learned from working on DriverPass is that it's easy to overlook smaller details, especially when creating diagrams. I had to go back and make changes after noticing missing information and mistakes in some of my diagrams. In future projects, I would spend more time planning things out, double-checking my work, and asking questions if something doesn't make sense. I think this would help me catch mistakes earlier and avoid having to make so many changes later on.
